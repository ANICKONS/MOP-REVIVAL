# Стенд эквивалентности MOPR6

Как стенд сравнивает игру с модом и без него. Требование 3, дизайн §10.

## Сейв: формат Easy Save 2

Проверено по декомпиляции `ES2.dll` игры (`_reference/decomp/ES2/`, ilspycmd 9.1) и на настоящем сейве.

`ES2.LoadAll` в `ES2.dll` есть (`ES2Reader.ReadAll`), но в игре для сравнения не годится:
- для каждого тега Transform или коллайдера он создаёт `GameObject` в сцене (`ES2Type.GetOrCreate`);
- результат — словарь объектов Unity без имён полей.

Поэтому сейв копируется в папку прогона (операция TestBot `savecopy`) и разбирается на хосте:
`MOPR6/Core/src/Es2/Es2Parser.cs`.

Формат файла (`ES2Writer.WriteHeader` / `Write*` / `WriteTerminator`, `ES2Reader.Next` / `ReadHeader`):

```
файл      = тег* [0]
тег       = 126, имя (строка BinaryWriter: 7-битная длина + UTF-8), int32 длина остатка, заголовок, данные, 123
заголовок = [127 — шифрование] [коллекция: 81 массив | 82 словарь | 83 список | 84 HashSet | 85 очередь | 86 стек]
            255, int32 хеш типа значения [, int32 хеш типа ключа — у словаря]
данные    = значение | int32 n, n значений (массив) | byte, int32 n, n значений (список и др.)
          | byte, byte, int32 n, n пар (словарь)
```

- Хеш типа — `ES2Type.GetHash(type.ToString())`, например `System.Single` → `0x6E3ED76B` (перенесено в
  `Es2Types.Hash`, проверено тестом на байтах настоящего сейва).
- Читатель принимает и старую форму заголовка с одним байтом-ключом типа (< 81). Игра её не пишет.
- Ключи 32 и 34 в этой сборке ES2 заняты несколькими типами (Enum, Matrix4x4, sbyte; decimal,
  SkinnedMeshRenderer). По байту-ключу они не сопоставляются, по хешу — однозначно.

## Детерминированный режим TestBot

Поля сценария `Deterministic` (по умолчанию выключен), `CaptureFps` (60) и `Seed` (20261017).

- `Time.captureFramerate = CaptureFps` ставится до нажатия Continue. Каждый кадр, в том числе кадры загрузки,
  продвигает игровое время ровно на 1/60 с.
- Готовность игрока считается в кадрах: `2 × CaptureFps` подряд с управлением.
- В этот момент («точка синхронизации») ставится `Random.seed = Seed + номер синхронизации` и начинается счёт
  кадров. После `savegame` и `reloadgame` синхронизация повторяется.
- В логе у каждой строки есть `f=<кадр от синхронизации>`. Шаг `waitframes` ждёт ровно N кадров.
- `WaitForSeconds` идёт по игровому времени, поэтому `SettleSeconds` и `wait` тоже детерминированы: 5 с = 300 кадров.

FPS в этом режиме не ограничен, но каждый кадр считается за 1/60 с: `captureFramerate` фиксирует и
`Time.deltaTime`, и `Time.unscaledDeltaTime`. Поэтому любой счётчик FPS внутри игры показывает ровно 60, а
игровое время идёт быстрее реального, если кадров больше 60 в секунду. Настоящая частота по логу бота
(600 кадров `waitframes` за реальное время), ваниль у дома: 73–79 кадров/с. Шаги `measure`, `profile`, `ab`,
`abtoggle` в детерминированном режиме пропускаются с сообщением в логе. Замеры — только в сценариях без
`Deterministic`.

Не детерминировано: число кадров загрузки зависит от реальной скорости загрузки. Игровое время в точке
синхронизации в двух прогонах ванили — 15,774 и 15,689 с, после перезагрузки — 51,958 и 56,356 с. Физика
успевает отработать разное число шагов, отсюда шум (ниже).

## Полный снимок сцены (`fullsnap`)

`TestBot/FullSnapshot.cs` → `fullsnap_<метка>.tsv`. Охватывает все объекты сцены, включая выключенные.
Исключены корни `MSCLoader*`, `MOPR_*` (объекты мода) и объекты TestBot. Ключи:

| Ключ | Значение |
|---|---|
| `<путь>.go` | activeSelf, слой, тег |
| `<путь>.cmp` | `enabled` каждого рендерера (+ режим теней), коллайдера и Behaviour |
| `<путь>.joint` | тип сустава, присоединённое тело, сила разрыва |
| `<путь>.pose` | мировые положение и поворот (объекты с Rigidbody или FSM) |
| `<путь>.rb`, `.vel` | kinematic, gravity, detectCollisions, сон, масса, ограничения; скорости |
| `<путь>#<FSM>.fsm` | enabled, RestartOnEnable, состояние, Started, Finished |
| `<путь>#<FSM>.<тип>.<имя>` | все переменные FSM (13 типов) |
| `@global.<тип>.<имя>` | глобальные переменные PlayMaker |
| `<путь>@<имя>.list` / `.table` | содержимое ArrayList/HashTable-прокси |

Путь устойчив между прогонами: `имя~k`, где k — номер среди соседей с тем же именем (по порядку детей; корни с
одинаковым именем — по instance id). Числа — `"R"`, `InvariantCulture`. Сжатие gzip в игре не используется:
`GZipStream` в Mono Unity 5 требует нативную библиотеку.

Первая строка — `#frame<TAB>N`. У дома: 118 807 ключей, 36 992 объекта, 6 815 FSM, 0,5 с на снимок, 10 МБ.

## Копия сейва (`savecopy`)

После `savegame` (игра сохраняет и выходит в меню, бот загружает её снова) шаг `savecopy <метка>` копирует
`Application.persistentDataPath` в `savecopy_<метка>/`. `test-run.ps1` забирает эти папки в папку прогона.
Сейв игрока восстанавливается и проверяется по MD5, как раньше.

## Сравнение: `EquivCompare equiv`

```
EquivCompare equiv --a <ваниль A> --b <ваниль B> --m <мод> --scenario <имя> --out <папка>
                   --tolerances MOPR6\Equiv\tolerances.json --expected MOPR6\Equiv\expected.json
```

Контрольные точки — каждый `fullsnap_*.tsv` и каждая `savecopy_*`. Классы и правила — `Core/src/Snapshot`
(дизайн §10.4). Отчёт: `report.md`, `report.json`. Код выхода 1, если есть необъяснённые.

## Ввод и консоль во время прогонов

- В детерминированных прогонах TestBot включает блокировку ввода (`InputLock.cs`, поле сценария `LockInput`,
  по умолчанию включено). Перехватываются cInput, `MouseLook`, `FPSInputController` и PlayMaker-действия
  чтения ввода — 43 точки. Причина: окно игры получает фокус, и ввод человека за компьютером доходит до игры.
  За один вечер это было в каждом прогоне: движение мыши, Mouse0, Escape, Alt+Tab. Без блокировки игрок
  поворачивался и ходил, и прогон расходился с остальными. Ввод всё равно считается: `report.json` →
  `InputFrames`, `InputKeys`, `InputLocked`. Прогон с вводом без блокировки `EquivCompare` не принимает.
- Консоль MSCLoader открыта весь прогон, в меню и в игре (`ConsoleKeeper.cs`, поле сценария `ShowConsole`,
  по умолчанию включено). MSCLoader закрывает её при старте и после загрузки сцены, бот открывает снова
  (проверка каждые 16 кадров). Консоль одинаково открыта у всех вариантов.

## Калибровка `full` (задача 11, 28–29.10.2026)

Набор `full`, по 3 прогона ванили и 1 прогон пустого MOPR6 на сценарий (`_testruns\equiv-20261028-230452`).

Трёх прогонов ванили мало. Значение, которое меняется случайно (клип радио кончается в реальном времени,
случайный таймер, стопка коробок оседает то так, то иначе), иногда совпадает во всех трёх прогонах ванили и
отличается в прогоне мода. Проверка «оставь один прогон ванили и сравни его с двумя другими» на старых допусках
давала 22–594 необъяснённых на сценарий.

Решение — выученная модель шума (`Core/src/Snapshot/NoiseModel.cs`, `MOPR6/Equiv/noise.json`): каждый ключ,
который разошёлся между прогонами ванили хоть одного сценария, считается шумом во всех сценариях. Индексы
одинаковых соседей (`~1`, `~4`) приводятся к `~*`. В отчёте такой ключ виден как шум с причиной
`learned: varied in vanilla (<сценарий/точка>)`. Модель пополняется: `equiv.ps1 -LearnNoise` или
`EquivCompare noise learn --runs runs.json --out noise.json`.

Сейчас в модели 4 085 ключей из шести сценариев. Добавлено одно правило `Volatile`: стопка коробок
аккумуляторов `r20 battery box(Clone)` в гараже из сейва автора (2–4 см, до 2°, разошлась в 6 из 9 проверок).

Итог для пустого MOPR6 с моделью шума: `eq-home-yard`, `eq-save-load`, `eq-car-work`, `eq-teimo-buy`,
`eq-walkaway`, `eq-sleep` — 0 необъяснённых. Честная проверка «оставь один прогон ванили» (модель выучена без
него) — 0 в 12 из 18 случаев, 2–19 в остальных. Значит, у модели есть пробелы, и она пополняется с каждым набором
прогонов ванили.

## Настоящая езда (`autodrive`, 29.10.2026)

Старый `eq-perajarvi-trip` для сравнения не годился. Бот (`Driver.cs`) не вёл машину, а каждый шаг физики

двух игрок погибал. Камера смотрела на 61° вбок. Модель шума эти прогоны не учитывает.

Что найдено по шагам (`MOPR6/Scenarios/diag-drive.json`, прогоны `dd1`–`dd4`):

| dd2 | Зелёный Fittan кузена (`TRAFFIC/VehiclesDirtRoad/Rally/FITTAN`) проехал в 7 м и толкнул стоящую машину. Посадка через 30 кадров после телепорта к двери не срабатывала. | кузен выключается на весь сценарий одинаково во всех вариантах; перед посадкой 120 кадров |

| dd4 | 1 466 м, 40–50 км/ч, передачи 1→4, игрок жив, камера вперёд (0°). Водитель смотрел на точку в 15 м и мерил кривизну по углу поворота на 35 м — поворот замечал поздно и не тормозил. | новый водитель (ниже) |
| dd5 | 1 458 м, 783 замера: отклонение от полосы в среднем 0,12 м, максимум 0,98 м (на том же повороте), ударов нет, крен не меньше 0,966. | — |

Как устроено:
- `VirtualInput.cs` — «клавиатура» бота. Блокировка ввода перехватывает `cInput` (`GetAxis`, `GetKey*`,
  `GetButton*`) и при включённом виртуальном вводе отдаёт значения бота. Настоящая клавиатура и мышь игру
  по-прежнему не достигают. Значения ставятся в конце кадра и действуют весь следующий кадр.
- `AutoDriver.cs` — водитель. Маршрут готовится один раз: направление и кривизна в каждой точке, предельная
  скорость в повороте (боковое ускорение 2,2 м/с²). Руль — метод Stanley по переднему мосту: ошибка курса на
  2–8 м вперёд, поправка на боковое отклонение и угол руля самого поворота. Скорость — минимум из крейсерской и
  всех поворотов на 150 м вперёд (торможение 1,8 м/с²); при отклонении больше 1,5 м — медленнее. Передачи вверх
  только на прямой, вниз — при низких оборотах или когда мотор не тянет. След каждые 10 кадров и маршрут пишутся
  в `autodrive_trace.tsv` и `autodrive_route.tsv`. Имена осей и клавиш берутся из `AxisCarController` машины. В настройках игры включено
  автоматическое сцепление, бот с ним работает.
- Двигатель запускается через FSM замка зажигания (`IgnitionSatsuma|UseNew` → `Check key`, через 6 с
  `FINISHED`): стартёр, смесь, «Running» — как у игрока.
- Шаги сценария: `autodrive`, `autodrivestop` (`"now"` — отпустить всё сразу), `look` (взгляд по машине),
  `route` (точки маршрута и ближайшая к объекту), `placecar … Lateral` (сдвиг маршрута вбок).
- Пробы `watch`: `@up`, `@roll`, `@yaw`, `@kmh`, `@near:R` (ближайшее движущееся тело), `@yawin:<объект>`.
  Водитель пишет в лог `HIT` (резкая потеря скорости) и `OVERTURNED`.

Стенд на новой поездке (`_testruns\equiv-20261029-012416`, 3 ванили и пустой MOPR6): все четыре поездки
чистые, ударов нет, отклонение от полосы до 1,0 м, остановка на 1 515–1 529 м. Необъяснённых 57 (на старой
поездке было 1 362). Это значения симуляции двигателя и колёс: смесь, крутящий момент, износ свечей, топливо,
проскальзывание. Поездка не повторяется кадр в кадр, потому что водитель реагирует на физику, а физика немного
расходится между прогонами. Ваниль против ванили даёт столько же: 43, 54 и 160 при проверке «оставь один».
Следующий шаг — калибровка шума поездки: больше прогонов ванили и допуски для симуляции машины во время езды.

  141–149 с на тот же отрезок), поэтому за то же число кадров еда портится меньше;

- `MasterAudio/…/gear_grind6.cmp` — `SoundGroupVariationUpdater` включается на время звука, конец звука — по

- в поездке — состояние «мышь над деталью» правой двери и `Required2` приборной панели: машина
  останавливается в разных местах (1519–1529 м в 5 прогонах ванили, 1514–1515 м в обоих прогонах мода, в том числе
  в сборке без оптимизаций), и луч камеры водителя попадает в разные детали.

Сценарий `realtime-grep` (операция `fsmgrep "realtime=true"`) перечислил все такие действия: 4 536 в 2 000 FSM
(`Wait` 4 242, `EaseFloat` 221, `EaseColor` 64, остальные — `EaseVector3`, `iTweenRotateTo`, `FloatInterpolate`).
Детерминированный режим фиксирует только игровое время (`captureFramerate`), поэтому фаза этих FSM в данном кадре
зависит от скорости компьютера: более быстрый мод сдвигает её. В настоящей игре кадры не фиксированы, и настоящее
время совпадает с игровым — поведение то же.

Добавлены узкие правила с доказательствами: в `tolerances.json` нестабильными стали `*(itemx)#Use.f.Condition`
(все 17 продуктов), `*/LookTarget#Move*` (34 из 36), `*/TargetPoint#Direction*` (все 16), `MasterAudio/*.cmp`; в
`expected.json` — два правила только для `eq-perajarvi-trip` (`#Use.fsm` и `#Removal.b.Required*` деталей
Satsuma). Все 2 000 FSM целиком не исключались: среди них болты (`BoltPM#Screw`, 170) и детали, которые
проверяют `eq-car-work` и будущий сон скриптов.

После правил (`equiv.ps1 -Reuse`, без новых прогонов): **7 из 7 сценариев — 0 необъяснённых** с включёнными
системами.

Дальше: для этапа 3 (сон скриптов) реальное время лучше подменить в детерминированном режиме самого TestBot —
префикс на `FsmTime.RealtimeSinceStartup` PlayMaker, который считает время по кадрам. Тогда эти FSM станут
детерминированными и правила реального времени не понадобятся; это требует новых прогонов ванили.

## Реальное время PlayMaker по кадрам (этап 3, 30.10.2026)

Сделано: поле сценария `VirtualRealtime` (`TestBot/RealtimeClock.cs`), включено во всех `eq-*`.
Вместе с `captureFramerate` TestBot ставит префикс на геттер `FsmTime.RealtimeSinceStartup`. Часы — настоящее
время в момент установки плюс 1/60 с за каждый кадр после него. Через этот геттер реальное время читают все
действия PlayMaker: `Wait realTime`, `Ease*`, `Animate*`, `Blink`, `Flicker`, затемнения камеры.
`Time.realtimeSinceStartup` самой Unity (iTween, MasterAudio) остаётся настоящим: это внутренний вызов.

Зачем: сон скриптов ускорил кадры примерно на 20%, и `Database/PlayerDatabase` «Simulation» (шаг голода, жажды,
стресса раз в 45 с, `Wait realTime`) попал после снимка `home` в `eq-teimo-buy` вместо «до» — 13 ключей.

Найдено по дороге:

- `Time.unscaledTime` для этого не годится: в этой Unity он идёт по настоящим часам и при `captureFramerate`
  (0,849 и 0,790 с на 60 кадров в двух прогонах). Первая версия часов на нём не убрала сдвиг. Нынешняя версия
  проверена: ровно 1,000 с на 60 кадров, фаза «Simulation» в ванили и в моде совпала до 1 мс.
- Шаг `watch` с `Seconds > 0` считал длину по настоящим часам, поэтому быстрый мод снимал `woke` в `eq-sleep`
  на 600 кадров позже ванили (5161 против 4561). В детерминированном режиме длина теперь считается в кадрах.
  Из сценариев `eq-*` это касается только `eq-sleep`, для него ваниль прогнана заново.

Ваниль `full` прогнана заново с новыми часами (`_testruns/equiv-20261030-001022`, по 3 прогона). Со сном
скриптов 5 сценариев из 7 сразу дали 0 необъяснённых, в том числе поездка: правила реального времени для неё
больше не срабатывают.

## Журнал перед снимком и снимки картинки (этап 2)

- `fullsnap` в прогоне с MOPR6: если журнал не пуст, TestBot пишет его в `ledger_<метка>.txt`, вызывает
  `TestApi.RestoreAll` и только потом снимает сцену. Снимок показывает состояние игры, а всё, что журнал не
  вернул или что мод изменил мимо журнала, остаётся отличием (§3, проверка 5.3). Системы берут изменения снова на
  следующем такте. С системами этапа 1 журнал пуст — прежние результаты не меняются.
- `abshot`: игра на паузе (`timeScale 0`), снимок с системой выключенной и включённой (`Var: "ab"` — собственное
  A/B системы, например склейки), сравнение `scripts/ImageDiff.ps1`. Так картинку можно проверить в одном сеансе,
  без новых прогонов ванили; на паузе сами по себе меняются только счётчик FPS и полоски HUD.
- `abtoggle Var: "mopr6ab"` — A/B собственным переключателем системы (склейка остаётся построенной, рисуются то
  оригиналы, то склейка), без снятия и установки.
- Шум A/B блоками по 1 с: прогон, где обе половины оказались одинаковыми (старая DLL), дал от −0,04 до +0,10 мс
  медианы. Отличия меньше 0,1 мс этим методом не видны.
