# Сон скриптов (этап 3)

## Что сделано

Система `sleep.idle` (`Mod/Sleep/FsmSleep.cs`) — ступень 1 из дизайна §7. Это BoltSleep из 5.x, расширенный на
все ванильные FSM.

Простаивающая FSM всё равно стоит Unity двух вызовов за кадр (`Update`, `LateUpdate`). С быстрым путём этапа 1
это вызов через замену Harmony. Спящая FSM выключена: `enabled = false` при `RestartOnEnable = false`. Её нет в
обновлениях Unity и в списке PlayMaker, а состояние сохраняется.

### Кто засыпает

Статические условия проверяются один раз на компонент (кеш до смены сцены):

- FSM ванильная по инвентарю;
- это единственная `PlayMakerFSM` на объекте (несколько — попробовано, см. ниже);
- нет флагов посредников: `HandleTrigger*`, `HandleCollision*`, `HandleOnGUI`, `HandleFixedUpdate`,
  `HandleApplicationEvents`, `MouseEvents`. Посредник проверяет `Active` и выбросил бы событие;
- нет под-FSM.

Динамические условия проверяются при каждом обходе:

- FSM запущена, состояние вошло и закончено, активных действий нет;
- нет отложенного перехода и отложенных событий, все счётчики циклов равны 0 (проверка BoltSleep);
- нет переходов на системные события, которые Unity шлёт сообщением (видимость, загрузка уровня, мышь):
  выключенный компонент их не получает;
- FSM простаивает в том же состоянии не меньше 30 кадров и 0,5 с. Каждый вход в состояние начинает отсчёт заново;
- FSM не «беспокойная»: больше 5 пробуждений за 10 с дают запрет на 30 с, следующий запрет вдвое длиннее
  (до 600 с).

В сцене у дома около 1 900 FSM в списке PlayMaker и 1 150 кандидатов, засыпают 606–616. Остальные не кандидаты:

| Причина | FSM |
|---|---|
| несколько FSM на объекте | 754–812 |
| триггеры | 108–120 |
| посредники (мышь, OnGUI, FixedUpdate) | 30–34 |

### Как

Сон идёт через журнал. Сначала `FsmPause` (`RestartOnEnable = false`), затем `FsmSleep` (`enabled = false`).
Возврат идёт в обратном порядке, поэтому сохранение, главный выключатель и `mopr restore` будят всех сами.

Сторож `SleepSentinel` стоит на объекте спящей FSM. Когда объект выключают, он делает то, что сделал бы
`OnDisable` самой FSM: возвращает флаг перезапуска и вызывает `Fsm.Stop()`.

### Пути пробуждения

Каждый путь будит FSM до того, как событие обработано.

| Путь | Кого будит |
|---|---|
| `Fsm.ProcessEvent` | спящую FSM с переходом на это событие. Без перехода бодрствующая FSM только скопировала бы данные события; это сделано, остальное пропущено |
| `Fsm.BroadcastEvent`, `PlayMakerFSM.BroadcastEvent` | спящие FSM с переходом, до копирования списка |
| `Fsm.BroadcastEventToGameObject`, `Fsm.SendEventToFsmOnGameObject` | спящие FSM этого объекта (и детей) с переходом |
| `PlayMakerFSM.FindFsmOnGameObject` | спящую FSM этого объекта, всегда |
| геттер `Fsm.FsmList` (копия списка) | всех |
| `EnableFSM` (вход; выход со сбросом) | спящую FSM целевого объекта |
| `OnEnable` спящей FSM от кого-то другого (в том числе журнала) | её саму, состояние сохраняется |
| выключение объекта | сторож, см. выше |

### Несколько FSM на объекте (попробовано, выключено)

Дизайн (§7.1) разрешал сон только единственной FSM объекта, «пока не доказано обратное». Код сна теперь ведёт
список спящих на каждом объекте, но условие «единственная FSM» оставлено: после сохранения и загрузки стенд нашёл
отличие, которое не объяснено. Пути, которые обращаются к объекту, а не к одной FSM, по декомпиляции PlayMaker 1.6:

| Путь | Как выбирает FSM | Что делает сон |
|---|---|---|
| `BroadcastEventToGameObject` | все FSM объекта из списка | будит каждую спящую FSM объекта с переходом на событие |
| `SendEventToFsmOnGameObject` | FSM объекта по имени | будит спящую с этим именем |
| `FindFsmOnGameObject` | FSM объекта по имени | будит спящую с этим именем |
| `EnableFSM` | `GetComponents` по имени, без имени — первая | будит все спящие FSM объекта |
| выключение объекта | `OnDisable` каждой FSM в порядке компонентов | сторож проходит спящие в порядке компонентов |
| посредники триггеров, столкновений, мыши | только FSM с флагом `Handle*` | такие FSM не спят |
| переменные соседей (`GetFsm*`/`SetFsm*`) | `GetComponents` по имени | работают со спящей |

Результат (`stage4-quick`, 31.10.2026):

- кандидатов 1 842–1 875 вместо 1 116–1 157, спят 776–778 вместо 606–609;
- режим проверки — 0 расхождений у дома, у машины и в езде;
- своё A/B, блоки по 1 с: езда −0,98 мс (+17%), в машине на месте −1,01 мс (+20%). Заметно больше прежнего
  это не дало;
- стенд (`equiv-20261031-145314`): 6 сценариев из 7 чистые, но в `eq-save-load` после загрузки в моде
  `MaskedBearing2` (скрытые болты коренного подшипника 2) включён, а его FSM `Screw` запущены в состоянии `Idle`
  со стадией 8. В ванили объект выключен и FSM не запускались. Тот же сценарий с прежним условием —
  0 необъяснённых (`equiv-20261031-150908`).

Режим проверки этого не видит: в нём ничего не выключается. Что именно включает объект, не разобрано; до этого
несколько FSM на объекте не спят.

### Порядок в списке PlayMaker

`OrderKeeper` ведёт отметку каждой FSM. Обычный `OnEnable` получает новую отметку в префиксе, то есть до
`OnEnable` FSM, которые включат её действия. Разбуженная FSM возвращается на место своей отметки. Во всех
прогонах нарушений порядка 0, в том числе после 21 000 возвращений на место в A/B.

### Режим проверки («виртуальный сон», §7.7)

Ничего не выключается: FSM, которые заснули бы, учитываются как спящие. Расхождением считается:

- вход в состояние без пробуждения;
- событие через список без пробуждения;
- вызов `ProcessEvent` неизвестным путём (вызывающий метод берётся из стека).

## Анализ кода игры (задачи 37, 40)

Поиск по декомпиляции PlayMaker и `Assembly-CSharp` (вместо IL-скана `EquivCompare ilscan`):

- `PlayMakerFSM.FsmList` в PlayMaker читают `Fsm.FsmList`, `Fsm.BroadcastEvent`, `BroadcastEventToGameObject`,
  `SendEventToFsmOnGameObject`, `FindFsmOnGameObject`, `PlayMakerFSM.BroadcastEvent` и `PlayMakerGUI`. Все,
  кроме `PlayMakerGUI`, перехвачены. `PlayMakerGUI` берёт только активные FSM с OnGUI, а такие не засыпают.
- В `Assembly-CSharp` `Fsm.FsmList` читает только `PlayMakerCollectionProxy` (будит всех).
  `PlayMakerFSM.enabled` пишет только действие `EnableFSM` (перехвачено). `Active` или `Finished` чужой FSM
  читает только `RunFSM`, а под-FSM исключены.
- В сцене (`fsmgrep` по всем состояниям, включая незагруженные) `EnableBehaviour` встречается 40 раз и ни разу
  на `PlayMakerFSM` (Wheel, Drivetrain, ForceFeedback, CarDynamics). `DestroyComponent PlayMakerFSM` — 5 раз, и
  всегда на своём объекте: FSM, которая это делает, не спит.
- `EventData` не читает ни одна ванильная FSM.

## Проверки Unity (задача 38)

Отдельных тестов нет. Для ступени 1 они не нужны:

- включение компонента во время `Update` важно для таймеров (ступень 2), а у спящих FSM ступени 1 таймеров нет;
- если бы Mono встроил перехваченный метод в вызывающий код, событие дошло бы до виртуально спящей FSM мимо
  хука. Режим проверки считает такое «неизвестным путём», и на всех прогонах таких было 0.

## Найденные ошибки

- **`__state` в Harmony 1.x.** Префикс и постфикс `OnEnable` передавали состояние через `__state`. Harmony 1.x
  объявляет эту переменную только для префиксов. `UnpatchAll` снимает префикс первым и не может собрать замену
  с одним постфиксом (`KeyNotFoundException`). В результате система не снималась, а после повторной установки
  постфикс работал дважды и портил порядок. Теперь состояние передаётся через свой словарь.
- **Отметка после вложенных включений.** Отметка ставилась в постфиксе, после `OnEnable` FSM, включённых
  действиями этой FSM. Теперь она ставится в префиксе (тест `A_stamp_taken_before_nested_enables_keeps_the_list_order`).
- **Счёт нарушений порядка.** Одна FSM не на месте считалась столько раз, сколько FSM она «перепрыгнула». Теперь
  она считается один раз.

## Реальное время в стенде

`full` со сном дал отличия в `eq-teimo-buy` (13 ключей) и в поездке (3 ключа). Они не от логики сна:

- `Database/PlayerDatabase`, FSM `Simulation`, раз в `SimulationRate` секунд **реального** времени (`Wait realTime`)
  добавляет голод, жажду, стресс и т. д. Со сном кадры примерно на 20% быстрее, и шаг пришёлся после снимка
  `home`, а не до него. В режиме проверки (всё бодрствует, медленнее) шаг был на месте: через 11,9 с после
  телепорта, как в ванили.
- В поездке колесо RL и `SuspDamage` (`Wait 10 s realTime`) зависят от траектории, а она — от реального времени.

Поэтому в TestBot появилось поле сценария `VirtualRealtime` (`RealtimeClock.cs`). В детерминированном режиме
`FsmTime.RealtimeSinceStartup` PlayMaker считает кадры: 1/60 с за кадр. Под это попадают все действия PlayMaker с
реальным временем: `Wait`, `Ease*`, `Animate*`, `Blink`, `Flicker`, затемнения камеры. `Time.realtimeSinceStartup`
самой Unity (iTween, MasterAudio) остаётся настоящим: это внутренний вызов, его не перехватить. Поле включено во
всех сценариях `eq-*`, ваниль прогнана заново (`_testruns/stage6/vrt`). Подробности — `harness.ru.md`.

## Эквивалентность

Ваниль с часами по кадрам, по 3 прогона на сценарий; мод — точные системы и сон:

| Сценарий | Необъяснённых |
|---|---|
| дом и двор, сохранение и загрузка, работа с машиной, поездка, уход от дома | 0 (с первого прогона) |
| сон в кровати | 0 после исправления `watch` (длина по кадрам) и новой ванили |
| покупка у Тейму | 0 во втором прогоне мода. В первом в одной точке разошлись футболисты (`SOCCER/LOD/KID1`, `KID2`): ни одна их FSM не спала, и второй прогон этого не повторил |

Режим проверки на сценарии Тейму — тоже 0. Полный прогон `full` с настройками по умолчанию одним заходом не
закончен.

## Решение

`sleep.idle` включён по умолчанию.

## Замеры (29.10.2026, 1280×720)

Своё A/B системы (A — все проснулись, хуки на месте; B — снова спят), блоки по 1 с, медиана кадра:

| Где | Медиана | |
|---|---|---|
| езда | −0,95…−1,08 мс | +8,2…8,3% |
| в машине на месте, двигатель работает | −2,41 мс | +26,1% |
| гостиная | −1,45…−2,63 мс | +20…30% |
| у машины, 6,5 м | −0,56 мс | +4,6% |

Блоки по 3 с дают то же, что по 1 с (гостиная −2,73 мс). A/B через снятие и установку системы блоками по 6 с
показал меньше (−0,68 мс), потому что в каждый блок B входит засыпание и сама установка. Поэтому проверено ровными
окнами: 15 с без системы, 15 с с ней (через 8 с после установки), дважды:

| Где | Без сна, медиана | Со сном, медиана | Разница | Средний FPS |
|---|---|---|---|---|
| гостиная | 8,89 / 9,45 мс | 7,37 / 7,37 мс | −1,80 мс | 103 → 118 (+14%) |
| у машины | 11,08 / 11,16 мс | 9,58 / 8,80 мс | −1,93 мс | 95 → 105 (+10%) |

Системы этапа 1 в обоих случаях включены.

## Стоимость обслуживания (задача 43)

В отчёте системы строка `upkeep`: время тика (`Stopwatch`) и время хуков, когда есть спящие FSM.

- Тик: 23–52 мкс за кадр, хуки: 3–6 мкс за кадр (13–21 вызов за кадр). Это 2–4% экономии, цель — меньше 5%.
- Сбор кандидатов раз в 30 с стоил 7–18 мс одним кадром. Теперь статические условия кешируются на компонент.
